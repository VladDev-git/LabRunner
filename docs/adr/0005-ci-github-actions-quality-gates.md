# ADR-0005: Безперервна інтеграція на GitHub Actions, Quality Gates і незмінні образи в GHCR

- **Статус:** Accepted
- **Дата:** 2026-11-26
- **Лабораторна:** №3

## Контекст

Код LabRunner живе в одному Gradle-монорепозиторії: два серверні сервіси (Docker-образи), спільні контракти та мобільний клієнт Kotlin Multiplatform для Android та iOS. Потрібно, щоб жодна зміна не потрапляла в `main` без автоматичної перевірки якості, тестів і безпеки, а артефакти для розгортання (лаба з Kubernetes) були відтворюваними й незмінними.

Розглянуті альтернативи CI: GitLab CI (потребує міграції репозиторію), Jenkins (власний сервер і підтримка), CircleCI / Bitrise (окремий сервіс; Bitrise добре підходить для мобільних, але не для серверних образів). Реєстр: Docker Hub (окремі облікові дані, ліміти на завантаження), Google Artifact Registry (з'явиться разом з GKE).

## Рішення

1. **GitHub Actions + GitHub Container Registry (GHCR).** Код, CI та образи живуть в одному місці; для публікації використовується короткоживучий `GITHUB_TOKEN` з правом `packages: write` лише в джобі збирання образів, окремі секрети не потрібні. Для публічного репозиторію хмарні раннери (зокрема macOS для iOS) безкоштовні.
2. **GitHub Flow.** `main` завжди стабільна; зміни — у короткоживучих гілках `feat/*`, `fix/*` і потрапляють у `main` лише через Pull Request. Правило захисту гілки забороняє прямий push і вимагає проходження всіх перевірок CI.
3. **Quality Gates (Shift Left, Fail Fast)** у `.github/workflows/ci.yml`:
   - `lint` — ktlint для всіх Kotlin-модулів, Android Lint (`abortOnError`), Hadolint для Dockerfile;
   - `test` — unit-тести, інтеграційні тести з Testcontainers (PostgreSQL 16), Android unit-тести і debug APK;
   - `ios` — тести спільного коду на iOS-симуляторі та iOS-фреймворк (macOS-раннер);
   - `security-fs` — Trivy: вразливості залежностей (за `gradle.lockfile`), помилки конфігурації, секрети; SARIF у GitHub code scanning;
   - `image` — збирання образу, Trivy-сканування саме цього образу, публікація в GHCR лише для `main` і тегів.
   Поріг: будь-яка CRITICAL або HIGH вразливість, для якої існує виправлення, блокує злиття.
4. **Відтворюваність:** залежності runtime закріплено в `gradle.lockfile`; сторонні GitHub Actions закріплено за SHA коміту (захист від підміни тегів — атака на ланцюг постачання).
5. **Незмінні теги образів** замість `:latest`: `sha-<короткий хеш коміту>` для кожного коміту в `main` і SemVer (`0.3.0`, `0.3`) для Git-тегів `vX.Y.Z`. Принцип Build Once, Deploy Anywhere: той самий образ проходить усі середовища.

## Наслідки

- Неякісний або вразливий код зупиняється до злиття; розробник бачить причину безпосередньо в Pull Request.
- Повний конвеєр триває кілька хвилин (найдовше — iOS на macOS); кеш Gradle і шарів Docker (`type=gha`) скорочує повторні запуски.
- Нові CVE з'являються щодня, тому зелена збірка вчора не гарантує зеленої сьогодні: оновлення залежностей стає регулярною задачею (наступний крок — Dependabot / Renovate).
- Правило «мінімум 1 схвалення» не застосовується: у проєкті один розробник, тому замість рев'ю обов'язковими є автоматичні перевірки.
