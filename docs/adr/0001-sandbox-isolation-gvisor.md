# ADR-0001: Ізоляція виконання недовіреного коду (ефемерні Kubernetes Job у gVisor)

- **Статус:** Accepted
- **Дата:** 2026-11-26
- **Лабораторна:** №1

## Контекст

Ядро системи — запуск довільного коду студентів, який може містити нескінченні цикли, «форк-бомби», спроби читання секретів або атаки на мережу кластера. Запуск контейнерів через Docker-сокет на воркері фактично дає коду root-доступ до вузла. MicroVM (Firecracker) дають найсильнішу ізоляцію, але потребують bare-metal вузлів і власної оркестрації.

## Рішення

- Кожна здача виконується в окремому одноразовому Kubernetes Job з `RuntimeClass: gvisor` (GKE Sandbox) на виділеному node pool з taint.
- Pod запускається від non-root користувача, з `readOnlyRootFilesystem`, без capabilities і без токена service account. Ліміти CPU / RAM задаються в маніфесті, `activeDeadlineSeconds` обриває зависання.
- `NetworkPolicy` забороняє весь трафік, крім завантаження коду й тестів з Object Storage за короткоживучими pre-signed URL.
- Результат повертається як JSON-звіт, який зчитує Runner Orchestrator.

## Наслідки

- Компрометація sandbox не дає доступу ні до вузла, ні до БД, ні до секретів. Навантаження від перевірок не впливає на API.
- Компроміс: gVisor додає 10–30 % накладних витрат на системні виклики, холодний старт вузла триває 1–2 хв. Це компенсується попереднім масштабуванням за розкладом дедлайнів.
