# ADR-0002: Асинхронна модель перевірки через чергу (Redis Streams)

- **Статус:** Accepted
- **Дата:** 2026-11-26
- **Лабораторна:** №1

## Контекст

Перевірка однієї здачі триває 5–60 с, а перед дедлайном надходять сотні здач за хвилини. Синхронна обробка в HTTP-запиті призвела б до тайм-аутів у мобільних мережах, вичерпання потоків API та втрати здач під час перезапуску подів.

## Рішення

- Core API валідує й зберігає здачу зі статусом `QUEUED`, додає повідомлення в Redis Stream `labrunner:submissions` (`XADD`) і одразу повертає `202 Accepted`.
- Runner Orchestrator читає задачі через consumer group `orchestrators` (`XREADGROUP`) і підтверджує їх (`XACK`) лише після збереження результату.
- Непідтверджені задачі після тайм-ауту перепризначаються (`XAUTOCLAIM`), після 3 невдалих спроб переносяться в dead-letter stream.
- Статус доставляється клієнту через SSE / push-сповіщення (у лабі №2 — опитування API).

## Наслідки

- API залишається швидким під час піку, перевірки масштабуються незалежно (KEDA за довжиною черги).
- Доставка at-least-once вимагає ідемпотентності обробника за `submission_id` (повторна обробка завершеної здачі пропускається).
- Redis потребує AOF-персистентності та моніторингу довжини черги.
