# ADR-0007: Безперервне розгортання через self-hosted runner і стек спостережуваності Prometheus + Grafana

- **Статус:** Accepted
- **Дата:** 2026-11-27
- **Лабораторна:** №5

## Контекст

Після лаби №4 є відтворюваний сервер (Terraform + Ansible), а CI публікує незмінні образи в GHCR. Потрібно автоматично доставляти кожен коміт з `main` на сервер, перевіряти розгортання, бачити стан інфраструктури й застосунку та отримувати сповіщення про відмови. Перевірка нефункціональних вимог з лаби №1 (API p95 ≤ 250 мс, виявлення відмови ≤ 1 хв) потребує метрик.

Сервер — VM у ізольованій NAT-мережі гіпервізора KVM (ADR-0006): GitHub-hosted раннери не можуть підключитися до неї по SSH.

## Рішення

### Continuous Deployment
1. Джоба `deploy` у `.github/workflows/ci.yml` виконується лише для `push` у `main`, після всіх Quality Gates і публікації образів, на **self-hosted runner усередині VM** (`runs-on: [self-hosted, linux, labrunner-vm]`). Runner встановлюється роллю Ansible `github_runner` (архів перевіряється за SHA256, реєстрація короткоживучим токеном, служба systemd від користувача `labrunner`) і сам з'єднується з GitHub вихідним HTTPS — вхідний доступ до VM не потрібен.
2. Секрети (паролі БД, Redis, сховища, Grafana, токен Telegram) зберігаються в GitHub Environment **production**, у який можна деплоїти лише із захищених гілок. На сервері вони записуються тільки в `/opt/labrunner/compose/.env` з правами 600.
3. Розгортання = `deploy/scripts/deploy.sh`: копіювання стеку, `docker compose pull` образів `sha-<коміт>`, `up --wait` (чекає healthcheck усіх сервісів), **post-deploy smoke test**: `GET /health` (статус UP і правильна версія) та наскрізна здача (API → Redis → Orchestrator → S3) до статусу `PASSED`. Помилка smoke-тесту робить джобу червоною й виводить логи сервісу.
4. Ризики self-hosted runner у публічному репозиторії: код із форків може виконатися на машині. Заходи: джоба розгортання не запускається для `pull_request`; увімкнено обов'язкове схвалення запусків від усіх зовнішніх учасників; runner має лише права користувача `labrunner` (група docker) і видаляється разом із VM.

### Спостережуваність
1. **Prometheus** (pull-модель, інтервал 15 с, зберігання 7 днів) збирає 5 таргетів у внутрішній мережі `monitoring-net`: сам себе, Core API, Orchestrator, Node Exporter (хост), cAdvisor (контейнери).
2. **Метрики застосунку** (Micrometer): RED для HTTP (`ktor_http_server_requests_seconds` з гістограмою для p95/p99), JVM, бізнес-метрики — прийняті здачі, черга перевірок (`labrunner_submissions_backlog`), результати й тривалість перевірок. Ендпоінти `/metrics` не публікуються: Caddy повертає 404 ззовні.
3. **Grafana** з provisioning як код: джерело даних, дашборди (`LabRunner — Service RED & Containers` і спільнотний `Node Exporter Full`), правила алертів, контакт Telegram. Доступна через reverse proxy за `/grafana/`; анонімний доступ лише на читання вмикається змінною середовища тільки в ізольованій лабораторній мережі.
4. **Алерти** (Grafana Alerting → Telegram Bot API): API Down і Orchestrator Down (`up < 1` протягом 30 с, оцінка кожні 10 с), частка 5xx > 5 % (2 хв), черга > 50 (5 хв). Повідомлення про відновлення (Resolved) увімкнені.
5. **Логи:** драйвер `json-file` з ротацією (`max-size 10m`, `max-file 3`) для всіх контейнерів; додатково `daemon.json` від Ansible. Централізований збір логів (Loki) — наступний крок.

## Наслідки

- Від злиття PR до оновленого сервера з перевіреною роботою — один автоматичний конвеєр без ручних дій; відкат = повторне розгортання попереднього тегу `sha-…`.
- Відмова сервісу виявляється за ~40 с (30 с `for` + інтервал оцінки) і доставляється в Telegram.
- Self-hosted runner прив'язаний до однієї VM: якщо VM недоступна, деплой чекає в черзі; у хмарі замість нього варто використовувати SSH-деплой або GitOps (ArgoCD) у Kubernetes.
- Prometheus і Grafana працюють на тій самій VM, що й застосунок: відмова VM вимикає й моніторинг. Для продакшену — винесений моніторинг або хмарний сервіс.
